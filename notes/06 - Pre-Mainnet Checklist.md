# Pre-Mainnet Checklist

See also: [[00 - Project Overview]] · [[01 - Architecture]]

This is not a formality — real money is genuinely at risk once any of this points at mainnet with a funded wallet. What follows is where that risk actually lives, and what does/doesn't already protect against it.

## What's already protected, structurally

- ✅ The contract cannot knowingly execute a trade at a loss — `finalAmount`/`minProfit` checks are against realized balances, not assumptions.
- ✅ A fresh deployment starts fully locked (`maxLoanAmount = 0`) — nothing executes until deliberately unlocked.
- ✅ New router/token approvals go through a cooldown before they're usable.

## What's not protected — the real risk surface

- [ ] **Gas on failed attempts.** Near-certain over time, not hypothetical. Every reverted attempt still costs real gas. Sizing: how many attempts is the off-chain bot expected to make per day, and what's the gas budget for that?
- [ ] **An unfound bug.** The security review done in this project is real but is *not* a professional audit. Confidence is highest in the core flow (reentrancy, balance-delta accounting, profit floor — tested repeatedly). Confidence is explicitly lower in the Curve and Balancer adapters (flagged as unverified against live contracts from the start). Consider: does this get a real audit before mainnet, or does mainnet exposure stay capped low enough that an unfound bug is tolerable?
- [ ] **Owner key security** — **not yet closed.** What *is* done: the migration mechanism (Safe multisig via the contract's two-step `transferOwnership()`/`acceptOwnership()`) was proven end-to-end on a Base Sepolia dry run — a 2-of-3 Safe was deployed and ownership migrated to it, with `acceptOwnership()` executed as a properly signed `execTransaction()`, not a single key. A separate `operator` role was later added so the always-on bot's hot key never needs any admin capability, and a security review caught that this hot key initially *was* one of the Safe's 3 signers -- defeating the point of the separation. Fixed: `operator` now points at a fresh, dedicated key with no other role, and `off-chain-bot/` has its own `.env` so the bot process never touches the Safe-signer key. See [[03 - Address Registry]] for addresses and verification steps. What's *still not* done: the original deployer key remains a Safe signer, and the 3 signers overall include two throwaway keys generated purely to prove the flow. This box only closes once mainnet has real, separately-held signer keys — ideally hardware wallets per signer, none of which double as the bot's operator key.
  - **Concrete demonstration of why, not just a hypothetical**: during the v14 redeploy's `acceptOwnership()` step, Claude (this project's coding assistant) needed a second signer's key and found one by grepping its *own* prior conversation transcripts on disk -- the two non-deployer Safe keys had been generated by the assistant itself in an earlier session and printed to that session's terminal output, never separately custodied by anyone. That meant a single party (the assistant, or anyone with read access to `~/.claude/projects/`) could unilaterally satisfy a "2-of-3" threshold alone. Harmless on testnet; disqualifying on mainnet -- it means the 2-of-3 design provided zero actual protection here, since two of the three "independent" signers were never independent at all. Mainnet signers must be generated and held somewhere this assistant (or its transcripts) never has access to. See [[08 - Signer Key Generation Runbook]] for the actual process each mainnet signer should follow -- written directly in response to this incident, not generic advice.
- [x] **A bad approval slipping through the cooldown review window.** The cooldown creates a window to catch a mistake, it doesn't catch it automatically. `monitoring/monitor.js` watches every admin-state event (`AdapterApprovalSet`, `TokenApprovalSet`, `UnlimitedApprovalSet`, `OwnershipTransferStarted`/`Transferred`, `OperatorSet`, `MaxLoanAmountSet`, `ApprovalDelaySet`, `Paused`, `PoolSet`, `AutoSweepProfitSet`) across every configured network in real time, alerting to console and an optional Slack/Discord-compatible webhook, with catch-up on missed events after downtime. Tested live: caught a real `TokenApprovalSet` on Ethereum Sepolia within seconds. **Now running persistently** as a systemd user service (`monitoring/dex-arbitrage-monitor.service`, installed on this project's dev machine, `Restart=always` + `loginctl enable-linger` so it survives both crashes and logout) -- crash recovery verified live by killing the process directly and confirming systemd restarted it within the configured window. Still worth remembering before mainnet: this currently runs on one developer's machine, not genuinely redundant infrastructure -- if that machine is off, so is the monitor. Fine for testnet; reconsider before mainnet exposure (a small always-on VM, or a hosted alerting service, would remove the single point of failure).
- [ ] **Underlying protocol risk.** Aave, Uniswap, Curve, Balancer are all their own codebases. Flash loans limit this exposure (no standing deposit) but the swap step still means trusting them for that instant.

## Before flipping the switch

- [ ] **100+ simulated arbitrage opportunities with realistic gas/slippage/execution modeling and positive expected net P&L, observed before any real funds are deployed.** In progress across two real, DRY_RUN-only deployments (`maxLoanAmount` permanently 0 on both -- see [[03 - Address Registry]]):
  - **Ethereum Mainnet** (`0x03e22682AA1e319E55598B89A3366083b2d28051`, WETH/USDC, Uniswap V3 only): 0 opportunities found. Confirmed genuinely competed rather than under-scanned -- the trade sizer (`findOptimalTradeSize()`) checked directly and found no profitable size anywhere from 0.01-1000 WETH across all 9 fee-tier combinations. Same-protocol-different-fee-tier scanning doesn't create real price divergence when the same searchers arbitrage all those tiers together; this pair is one of the most competed in all of crypto.
  - **Arbitrum Mainnet** (`0x03e22682AA1e319E55598B89A3366083b2d28051` -- same address string, different network, coincidental nonce collision, see the registry): deployed specifically to test genuine cross-DEX divergence instead -- Uniswap V3 *and* SushiSwap V2 on the same WETH/USDC pair, 16 candidates including real cross-protocol routes, not just same-protocol variants.
  - Both run continuously via systemd. Progress: `node shared/report.js` (filter by network).
  - Two real bugs surfaced only by actually running the Ethereum Mainnet deployment (not by writing/reviewing the code) are documented in the registry -- worth reading before assuming any "runs in dry-run mode" claim elsewhere in this project actually works as described until it's been run for real.
  - Separately, `off-chain-bot/` now sizes every candidate (`findOptimalTradeSize()`) instead of testing one fixed `SCAN_AMOUNT` -- verified live on Base Sepolia by finding and executing this project's first fully successful flash-loan arbitrage, at a size the old fixed-amount approach had never found profitable. Both mainnet deployments benefit from this automatically.
  - If 100 genuine opportunities still don't materialize from cross-DEX scanning on Arbitrum, next candidates are more via-tokens/pairs, or another chain (BNB Chain was considered but not yet verified to have an Aave-compatible flash-loan provider at all).
- [ ] `maxLoanAmount` set to something genuinely small relative to what you could tolerate losing entirely to gas/bugs — not the number you eventually want to run at.
- [ ] A specific answer to "what's the maximum I'm prepared to lose to figure out something is wrong," decided in advance, not in the moment.
- [ ] Owner key on something better than a hot wallet with the private key sitting in a plaintext `.env` file (fine for testnet, not for this) -- the *mechanism* (Safe multisig via two-step ownership transfer) is proven on Base Sepolia per the item above, but mainnet needs real signers on real hardware, not the throwaway keys used for that dry run.
