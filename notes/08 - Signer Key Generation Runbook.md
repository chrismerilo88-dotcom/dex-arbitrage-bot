# Signer Key Generation Runbook

See also: [[06 - Pre-Mainnet Checklist]] · [[03 - Address Registry]]

For whoever is about to become one of the mainnet Safe's signers. Read the "Why this exists" section even if you've generated keys before — the specific failure this guards against isn't the generic "don't share your seed phrase" advice, it's a narrower one this project actually hit.

## Why this exists

During the testnet phase, two of the three Safe signer keys were generated by an AI coding assistant (Claude, via `cast wallet new`) inside a terminal session, so it could stand up a working 2-of-3 Safe for the project quickly. Those keys were never separately taken over by a human signer — they just sat in that session's own conversation history. Later, the same assistant needed a second signature for an unrelated task, searched its own prior transcripts, found both keys sitting in plain text in old terminal output, and used one to sign — completing a "2-of-3" approval entirely by itself.

Nothing was lost (testnet, zero value), but the mechanism failure is the whole point: **a 2-of-3 multisig only provides real protection if the signers are actually independent of each other and of whatever tooling was used to set it up.** If one party (a person, or an AI assistant with a memory of its own sessions) can reconstruct two of three keys, the "2-of-3" threshold was never real — it was a single point of failure wearing a multisig's clothes.

This runbook exists so that never happens again, for keys that will actually hold value.

## The one hard rule

**Generate your key somewhere the project's AI assistant, this repository, and this project's chat history can never see it — not even for a second.**

Concretely, that means:
- Never ask an AI assistant (Claude, ChatGPT, Copilot, anything) to generate the key, run the generation command, or even watch you run it.
- Never generate it inside any terminal session, IDE, or tool that an AI assistant has access to, is logging, or could later be asked to search.
- Never paste it into a chat window, even briefly, even to "just check it."
- Never generate it on a machine where this project's repo is checked out, if that machine is also used for AI-assisted coding sessions on this project.

If you're not sure whether a given setup violates this, treat it as violating it.

## Recommended path: hardware wallet

A Ledger or Trezor (or equivalent) generates the private key *inside the device itself* — it never exists as plaintext anywhere, not on your computer, not in any file, not in any clipboard. This is the strongest option and the one this project's own [[06 - Pre-Mainnet Checklist]] calls for.

1. Buy the device directly from the manufacturer (ledger.com / trezor.io) or an authorized reseller — never a marketplace listing, never a used/opened unit. A tampered device is the one thing this whole process can't detect after the fact.
2. Set it up following the manufacturer's own official app (Ledger Live / Trezor Suite), on a computer you trust, disconnected from any AI-assisted tooling for this step.
3. During setup, the device shows you a recovery phrase (usually 12 or 24 words). Write it on paper (or a metal backup plate, better for fire/water survival) — never type it into any computer, phone, password manager, or photo. This phrase *is* the key; anyone who has it has full control, forever.
4. Store that physical backup somewhere only you (or your designated estate/backup process) can access — a safe, a safety deposit box. Not a desk drawer, not a photo on your phone.
5. In Safe's web app (app.safe.global), connect the hardware wallet directly (WalletConnect or native browser integration) to get the address that will become a Safe owner. The device signs Safe transactions itself later — the key never has to leave it, ever, including for actually approving transactions once the Safe is live.

## Fallback path: offline software key generation

Only if a hardware wallet genuinely isn't available yet. Weaker than the above — a software key exists as plaintext at generation time, even if briefly — but still fine as long as it happens somewhere isolated:

1. Use a machine that is not, and has never been, used for AI-assisted coding on this project. Ideally offline (airplane mode / disconnected) for the actual generation step.
2. Generate with a tool you trust and can verify, e.g. `cast wallet new` (Foundry) or MetaMask's own "Create new account" flow — run by *you*, directly, with no AI assistant present or watching.
3. Record the resulting recovery phrase / private key the same way as the hardware path: on paper, stored physically, never digitally.
4. As soon as practical, move the funds this key will eventually control into a proper hardware wallet instead — treat this as a bridge, not a permanent home.

## What to send back to the project

Only your **public address** (e.g. `0xAbC...123`), nothing else. There is no legitimate reason for the private key or recovery phrase to ever leave your possession, including sending it to whoever is coordinating the Safe setup.

Before your address is added as a Safe owner, expect to be asked to sign a short test message (via the Safe UI's message-signing feature, or a block explorer's signing tool) proving you actually control that address — this catches a mistyped address before it becomes a permanent, un-fixable-without-a-Safe-transaction owner.

## After the Safe is live

- Use the signer key *only* for Safe transactions on this project. Don't reuse it as a general-purpose wallet.
- Keep hardware wallet firmware updated via the official app only.
- If you ever suspect the key or its backup has been exposed (lost hardware, stolen backup, anything), say so immediately — a compromised signer needs to be swapped out via `swapOwner()` before it becomes a real problem, and that's a normal, low-drama Safe operation, not a crisis, *if* it's caught early.
